# Playbook de Incidente: Banco de Dados D1 Indisponível (SEV-1)

## 1. Como Identificar?
- **Sintoma:** O Frontend mostra erros constantes (Timeouts ou Erros HTTP 503).
- **Alerta Cloudflare:** Falhas nas execuções de Worker e taxa massiva de exceptions contendo `D1_ERROR` ou `UNIQUE_CONSTRAINT_FAILED`.
- **API Analytics:** Volume de leitura/escrita despenca a zero, enquanto a taxa de erros HTTP sobe drasticamente.

## 2. Qual o Impacto?
- O Sistema Central (Account Platform) fica **totalmente paralisado**.
- Impossibilidade de login, operações financeiras e votos.
- A integridade dos dados pode estar sob ameaça de corrupção caso seja uma falha de migração forçada.

## 3. Como Mitigar?
1. **Verificar Status Cloudflare:** Cheque a [Página de Status da Cloudflare](https://www.cloudflarestatus.com/) para descartar problemas globais no D1.
2. **Modo de Manutenção:** Ative a Response Worker de modo de manutenção (Redirecionando todas as rotas para um template HTML estático "Em Manutenção").
3. **Verificar Migrações:** O erro ocorreu logo após um *deploy*? 
   - Se sim, há uma inconsistência de `migrations`. Reverta o deploy do Worker pelo painel da Cloudflare (*Deployments -> Rollback*).

## 4. Como Restaurar (Se houver corrupção de dados)?
- Abra a documentação em `docs/BACKUP_RECOVERY.md`.
- Verifique o último timestamp válido (Point-In-Time) usando:
  `npx wrangler d1 time-travel info gov-db --env production`
- Execute a restauração de Time-Travel no terminal.
  > [!CAUTION]
  > Isto causará a perda de todos os registros (cadastros e tesouraria) efetuados **após** a hora da falha. Anuncie o corte aos stakeholders.

## 5. Como Validar a Recuperação?
- Remova o Worker de Modo de Manutenção.
- Dispare o Smoke Test via Github Actions (`GET /health/live` e `GET /health/ready`).
- Faça um login manual em Staging/Production usando a conta `sandro_ceo@asppibra.com` e verifique o Dashboard Financeiro.
